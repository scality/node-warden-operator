# Contributing

Thanks for contributing to node-warden-operator. This guide covers the workflow and the
conventions the codebase follows. For what the operator does see the [README](README.md); for
how it is built and why see [DESIGN.md](DESIGN.md).

## Development environment

The repository ships a devcontainer (`.devcontainer/`) with Go and the pinned tooling
(golangci-lint, kind, kubebuilder, kubectl, kustomize) already installed. Outside the
devcontainer you need Go 1.26+ and those tools on your `PATH` for the full workflow.

Everyday commands:

```sh
make test               # unit + envtest suite
make test-e2e           # end-to-end on a kind cluster
make lint               # golangci-lint
make manifests generate # regenerate CRD, RBAC and deepcopy (controller-gen)
make build              # build the manager binary
make docker-build       # build the container image
```

## Architecture

The architecture - the functional core / imperative shell and what each part owns - lives in
[DESIGN.md](DESIGN.md#architecture-functional-core-imperative-shell). Read it before adding a
type or changing the reconcile flow, so your change lands where it belongs.

## Coding conventions

- **Errors**: `github.com/scality/go-errors`, imported unaliased as `errors`. Define
  package-level `ErrXxx` sentinels and wrap at the failure site with
  `errors.Wrap(ErrXxx, errors.WithDetail(...), errors.WithProperty(...), errors.CausedBy(rawErr))`
  so `errors.Is` keeps matching the category.
- **Keep the core pure**: the decision lives in a pure `Decide` function that takes the
  observed facts and returns a plan; it never touches the cluster. Status is produced by the
  core and written once per reconcile - no multi-writer status updates.
- **Tests**: Ginkgo + Gomega, one `RunSpecs` suite per package (`DescribeTable` for
  table-style cases). The controller and the CEL-validation suites use envtest; the pure-core
  suite is plain specs and needs no cluster. Run `make test` (sets up envtest) and
  `make test-e2e` (kind).
- **Generated code**: CRD manifests, RBAC and deepcopy are generated by controller-gen
  (`make manifests generate`), committed, and CI fails if they are stale. Never edit generated
  files by hand.
- **Linting & formatting**: `make lint` must pass.

## Running locally

`make test-e2e` validates the full behavior automatically on a kind cluster. To iterate by
hand against a real cluster:

```sh
kind create cluster
make install                     # install the CRD
make run                         # run the operator on the host (foreground)
kubectl apply -k config/samples/ # apply a NodeRemediationPolicy
```

Because the operator reacts to `Node` conditions, exercising a policy end to end means driving
a matching condition onto a node (the e2e suite does this by patching the node status).

## Commits and pull requests

- Conventional-commit subjects with an explicit action verb, e.g. `feat: ...`, `fix: ...`,
  `chore: ...`, and a short (< 50 char) summary.
- Keep each commit a single coherent change. Reference the tracking issue with a trailing
  `Issue: <ticket>` footer, never in the subject.
- Make sure `make test` and `make lint` pass before opening a PR, and keep PRs focused.

## Keep the docs in sync

Treat the docs as part of the change, not an afterthought. In the same PR:

- a change to behavior, the CRD, flags, or output -> update the [README](README.md);
- a change to architecture or a design decision -> update [DESIGN.md](DESIGN.md);
- a change to conventions or workflow -> update this file.
